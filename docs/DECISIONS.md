# Лог решений

Почему проект устроен так, а не иначе. Новые решения дописываются внизу.

## Инструменты

Проект делается вместе с Claude Code (модель Claude Opus 5.5) в десктоп-приложении Claude. Агент пишет код, тесты и документацию; продуктовые решения, выбор задания и проверка результата — за мной.

## 1. Стек: TypeScript на сервере и клиенте

- **Backend:** Node.js 24 + Fastify 5. Fastify быстрый, с хорошей типизацией и плагином для WebSocket.
- **Frontend:** React 19 + Vite 8 + TanStack Query (кэш серверных данных и его инвалидация по событиям из WebSocket).
- **Общий пакет `@se/shared`:** zod-схемы и логика денег (деление, балансы, переводы). Сервер и клиент используют один и тот же код, поэтому превью долей в форме и расчёт на сервере не могут разойтись.
- **БД:** PostgreSQL 17 + Drizzle ORM. Drizzle — тонкая типизированная обёртка над SQL, без «магии» ORM, миграции генерируются из схемы.
- **Почта:** Mailpit как локальный SMTP-ловец (требование 10 разрешает эмуляцию). Все письма видны на http://localhost:8025.

Почему TypeScript, а не Python: один язык и общие типы на обеих сторонах, а логика денег нужна и на клиенте (превью), и на сервере (источник правды).

## 2. Монорепо на pnpm workspaces

`apps/server`, `apps/web`, `packages/shared`. Пакет `shared` подключается исходниками (`exports` указывает на `.ts`): Vite и tsx компилируют его сами, отдельная сборка не нужна.

## 3. Деньги хранятся в целых копейках

Никаких float. Все суммы — целое число минимальных единиц валюты. Это убирает ошибки округления и делает правило «сумма долей = сумме расхода» проверяемым точным равенством.

## 4. Балансы не хранятся, а вычисляются

Баланс участника = сколько заплатил − его доли в расходах ± подтверждённые погашения. Следствия:

- правка или удаление старого расхода автоматически пересчитывает всё, включая уже сделанные погашения (требование задания);
- сумма балансов в группе равна нулю по построению: каждый расход раскладывается на доли без остатка.

## 5. Минимальный набор переводов: точный перебор для обычных групп

Жадный алгоритм (крупнейший должник платит крупнейшему кредитору) даёт не больше n−1 переводов, но не всегда минимум. Контрпример: балансы +5000, +4000, +2000, −5000, −6000 — жадный даёт 4 перевода, оптимум 3 (пара +5000/−5000 сходится отдельно). Для групп до ~15 человек считаем точный минимум перебором разбиений на подгруппы с нулевой суммой; для больших групп — жадный алгоритм. Порог и поведение будут описаны в README.

## 6. Каналы уведомлений

Письмом (через Mailpit) — только то, что задание прямо называет письмом: приглашение по почте, напоминание должнику, итог при закрытии группы. Остальное («уведомление» о новом или изменённом расходе, запрос на подтверждение погашения) — уведомления в приложении через WebSocket. Web Push не делаем: service worker, VAPID-ключи и разрешения браузера усложняют проверку и не требуются заданием.

## 7. Дизайн до кода

Перед разработкой интерфейса составлен бриф для дизайна (`docs/design-brief.md`) со сквозным примером, на котором видны все состояния: деление с лишней копейкой, ожидающее погашение, разворот баланса после правки старого расхода.
